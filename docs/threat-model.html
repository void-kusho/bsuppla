Threat Model & Security Guarantees

This document defines the threat model for bsuppla, including attacker capabilities, security assumptions, guaranteed properties, and known limitations.

1. Scope & Assumptions

1.1 In Scope

  • Analysis of Docker/OCI container images via static filesystem inspection
  • Detection of supply-chain threats: malware, credentials, suspicious binaries, malicious configs
  • Execution on trusted host infrastructure (build servers, CI/CD runners, developer machines)
  • Integration into automated pipelines (GitHub Actions, GitLab CI, Jenkins, etc.)

1.2 Out of Scope

  • Runtime/behavioral analysis (process execution, network traffic, syscalls)
  • CVE/vulnerability database matching (no NVD integration)
  • Windows container images
  • Encrypted/polymorphic payload detection
  • Kernel-level exploits or host compromise
  • Social engineering or supply-chain attacks on the build pipeline itself

1.3 Core Assumptions

# Assumption Rationale If Violated
A1 Host OS/kernel is trusted bsuppla runs as user process; kernel mediates filesystem access Host compromise → all bets off
A2 Docker daemon (if used) is trusted Only used for pull/save; skipped via BSUPPLA_SKIP_DOCKER Daemon compromise → image tampering
A3 bsuppla binary is authentic Built from verified source; checksums verified Supply-chain attack on bsuppla itself
A4 Input image is untrusted Primary threat model assumption N/A — this is the threat
A5 Filesystem semantics are POSIX-compliant Relies on st_mode, symlink behavior, path resolution Non-standard FS → detection gaps

3. Adversary Model

3.1 Attacker Capabilities

The adversary controls the Docker image content and can:

  • Embed arbitrary files, binaries, scripts, configurations
  • Craft malicious ELF binaries (packed, stripped, corrupted headers)
  • Create symlink chains, deep directory structures, long paths
  • Embed files with unusual permissions (SUID, world-writable, sticky)
  • Hide payloads in alternate data streams, extended attributes
  • Craft tar archives with malformed headers, overlapping entries
  • Use case-insensitive filesystem tricks (if host FS permits)

3.2 Attacker Goals

  1. Code Execution: Trigger execution of malicious payload during analysis
  2. Evasion: Hide malicious artifacts from detectors
  3. Denial of Service: Cause analyzer crash, hang, or resource exhaustion
  4. False Confidence: Cause benign image to appear malicious (or vice versa)
  5. Information Leakage: Extract host filesystem data via path traversal

    6. 3.3 Attacker Limitations

    • Cannot execute code on host during analysis (enforced by design)
    • Cannot modify bsuppla binary or detector registry at runtime
    • Cannot access host network during analysis phase
    • Cannot escape extracted filesystem directory (chroot-like isolation)

    4. Security Guarantees

    Guarantee 1: Zero Code Execution (Theorem 1)

    No code from the analyzed Docker image is ever executed during analysis.

    Mechanism: Analysis uses only symlink_metadata, read_dir, File::open (read-only). No execve, fork, ptrace, dlopen. The Detector trait provides no execution capability.

    Guarantee 2: Deterministic Output (Theorem 2)

    Identical input image + configuration always produces identical findings.

    Mechanism: Pure functions throughout pipeline. No randomness, timestamps, hash maps with random seeds, or external state. Registry order is fixed at compile time.

    Guarantee 3: Memory Safety

    No buffer overflows, use-after-free, double-free, or data races in analysis code.

    Mechanism: Written in safe Rust. Zero unsafe blocks in detection logic. All file I/O uses std::fs safe abstractions.

    Guarantee 4: Detector Isolation (Theorem 4)

    A failure in one detector cannot affect other detectors or the scanner.

    Mechanism: Detectors are Send + Sync trait objects. DetectorRegistry::detect calls each independently via filter_map. No shared mutable state.

    Guarantee 5: Path Traversal Prevention

    Analysis cannot escape the extraction directory or follow symlinks outside it.

    Mechanism: walk_dir uses symlink_metadata and skips symlinks entirely. Paths are resolved relative to extraction root. strip_prefix ensures all paths are contained.

    5.1 Detailed Attack Vectors

    5.1.1 Tar Archive Attacks

    • Absolute paths: Tar entries with /etc/passwd — mitigated by strip_prefix relative to extraction root
    • Symlinks: linkname=../../etc/passwd — mitigated by skipping symlinks entirely
    • Hard links: Multiple entries pointing to same inode — handled by tar crate
    • Long paths: >PATH_MAX — tar crate handles; filesystem may reject

    5.1.2 Filesystem Attacks

    • SUID/SGID binaries: Detected by SuidSgidDetector; never executed
    • Device files: mknod in tar — tar crate ignores or errors
    • Named pipes/sockets: Skipped by is_file() check
    • Extended attributes: Not read; no attack surface

    5.1.3 ELF Parsing Attacks

    • Malformed headers: goblin returns Err; detector returns None
    • Integer overflows: goblin uses checked arithmetic
    • OOB reads: Bounded by 5 MiB read limit
    • Infinite loops: Section header iteration bounded by file size

    5.1.4 Evasion Techniques

    Technique Example Detected? Notes
    Obfuscated miner binary Renamed xmrig, custom build Partial Name-based only; content hash not checked
    Encrypted payload Encrypted blob + stub decryptor No Static analysis cannot decrypt
    Polyglot file Valid ELF + valid script Yes ELF detector triggers on header
    Hidden in alternate stream NTFS ADS / macOS resource fork No Not extracted by tar on Linux
    Time-based trigger Malware activates after date No Static analysis cannot observe time
    Environment-dependent Checks for CI env vars No No execution = no env observation

    6. Mitigations

    6.1 Design-Level Mitigations

    • Zero Execution: Fundamental guarantee — no code path leads to execution
    • Read-Only Analysis: Extraction directory created fresh per scan; no writes to source
    • Symlink Rejection: Eliminates entire class of path traversal
    • Size Bounds: ELF parsing limited to 5 MiB; config files to 64/128 KiB
    • No Network in Analysis: Air-gap compatible by design
    • Immutable Registry: Detectors registered at compile time; no dynamic loading

    6.2 Operational Mitigations

    • Run in Container/VM: Additional isolation layer for defense-in-depth
    • Verify Binary: sha256sum bsuppla | grep -f checksums.txt
    • Use BSUPPLA_SKIP_DOCKER: Eliminates Docker daemon from TCB
    • Allowlist Review: Audit allowlist entries; don't over-suppress
    • Baseline Rotation: Regenerate baselines after verified image updates

    7. Known Limitations

    Limitation 1: Static Analysis Cannot Detect Encrypted/Encoded Payloads

    If malicious code is encrypted, encoded, or compressed with custom algorithms, static analysis cannot observe the plaintext. This is a fundamental limitation of static analysis.

    Mitigation: ELF detector flags packed/UPX binaries as suspicious; entropy analysis could be added.

    Limitation 2: No Behavioral/Runtime Visibility

    Malware that downloads payloads at runtime, checks environment, or uses time-based triggers will not be detected.

    Mitigation: Combine with runtime security (Falco, Tracee) for defense-in-depth.

    Limitation 3: Signature-Based Detection

    Crypto miner and risky tool detection relies on known name lists. Novel or renamed tools evade detection.

    Mitigation: Allowlist suppresses FPs; heuristic ELF analysis catches suspicious binaries regardless of name.

    Limitation 4: Linux-Only

    Analysis assumes Linux filesystem semantics (permissions, ELF, paths). Windows containers not supported.

    Mitigation: Document clearly; Windows support would require separate implementation.

    Limitation 5: No CVE/Vulnerability Data

    bsuppla does not match package versions against vulnerability databases.

    Mitigation: Run alongside Trivy/Grype/Clair for comprehensive coverage.

    Limitation 6: 5 MiB ELF Read Limit

    Very large binaries (>5 MiB) are only partially parsed. Could miss packer signatures in later sections.

    Mitigation: Most packers modify early sections; 5 MiB covers headers + early sections. Configurable if needed.

    8. Residual Risk Assessment

    Risk Likelihood Impact Overall Acceptance
    Encrypted payload evasion Medium High Medium-High Accepted — fundamental static analysis limit
    Novel malware not in signatures High Medium Medium Accepted — heuristic ELF + permissions catch many
    Tar parser vulnerability (Rust std) Very Low High Low Accepted — mature crate, fuzzed
    ELF parser vulnerability (goblin) Low Medium Low Accepted — safe Rust, bounded reads
    Symlink race (TOCTOU) Very Low Medium Very Low Mitigated — symlinks skipped entirely
    Path traversal in extraction Very Low High Very Low Mitigated — strip_prefix, clean dir
    Docker daemon compromise Low High Medium Mitigated — BSUPPLA_SKIP_DOCKER=1
    bsuppla binary supply-chain Very Low Critical Low Mitigated — signed releases, reproducible build

    8.1 Risk Acceptance Criteria

    The following residual risks are accepted based on:

    1. Fundamental limits: Static analysis cannot decrypt or observe runtime behavior
    2. Defense in depth: bsuppla is one layer; runtime tools address complementary threats
    3. Cost-benefit: Mitigating further would require dynamic analysis (breaking zero-execution)
    4. Transparency: Limitations documented; users can make informed decisions

    9. Security Testing

    9.1 Fuzzing

    • Tar parsing: cargo-fuzz on ingest::image::read_manifest_from_image
    • ELF parsing: cargo-fuzz on detectors::elf::elf_suspicious_detail
    • Config parsing: cargo-fuzz on package manager config parsers

    9.2 Property Testing

    • Determinism: proptest: same input → same output (1000 iterations)
    • Allowlist idempotence: allowlist(allowlist(x)) = allowlist(x)
    • Baseline symmetry: diff(A,B) + diff(B,A) = symmetric difference

    9.3 Penetration Testing

    • Malformed tar archives (tar-fuzz corpus)
    • Malformed ELF binaries (ELF-fuzz corpus)
    • Path traversal attempts (custom test suite)
    • Resource exhaustion (nested archives, sparse files)

    10. Incident Response

    10.1 If Malicious Image Analyzed

    1. No code executed — no immediate host compromise
    2. Findings logged with suspicion level
    3. Extraction directory auto-cleaned
    4. Review findings; update detectors if novel technique

    10.2 If False Negative Discovered

    1. Add test case to detector test suite
    2. Implement detection logic (1-line PathRule or new Detector)
    3. Run full test suite; verify no regressions
    4. Release patch version

    10.3 If False Positive Spike

    1. Add allowlist entry (glob pattern)
    2. If systemic: refine detector logic
    3. Run evaluation corpus; verify F1 maintained

    11. Conclusion

    The bsuppla threat model is built on a minimal trusted computing base (Rust stdlib + goblin + tar crates) with a clear trust boundary between the analyzer and the untrusted input image. The design provides strong guarantees:

    • Zero execution — mathematically enforced by design
    • Determinism — enables reproducible audits
    • Memory safety — eliminates entire vulnerability classes
    • Isolation — detector failures contained

    Residual risks are documented, accepted based on fundamental static analysis limits, and mitigated through defense-in-depth deployment recommendations.

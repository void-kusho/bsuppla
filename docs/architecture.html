System Architecture

This document provides a detailed architectural description of the bsuppla static analysis framework, including formal system model, design rationale, and verified properties.

1. Formal System Model

System Definition

The bsuppla analyzer is a deterministic function A: I × C → F where:

  • I = Set of Docker image tarballs (input)
  • C = Configuration (allowlist, baseline, output directory)
  • F = Set of findings with severity levels and suspicion assessment
Determinism

For any fixed input image i ∈ I and configuration c ∈ C, the analyzer produces identical findings: ∀i,c: A(i,c) = A(i,c).

The analysis pipeline is modeled as a composition of pure functions:

A = Report ∘ Filter ∘ Detect ∘ Extract ∘ Load ∘ Acquire
where:
  Acquire: I → Tarball          (docker pull/save, optional)
  Load: Tarball → Manifest      (parse manifest.json)
  Extract: Manifest → Filesystem (reconstruct layered FS)
  Detect: Filesystem → Findings (run detector registry)
  Filter: Findings → Findings   (allowlist + baseline)
  Report: Findings → Output     (format + suspicion level)

2. Design Goals

The architecture is driven by the following design requirements, ordered by priority:

Priority Goal Description Verification
Critical Zero Execution Never execute any code from analyzed images Theorem 1
Critical Memory Safety No buffer overflows, use-after-free, data races Rust type system
High Extensibility Support custom detection plugins without core modification Open/Closed Principle
High Testability Each detector independently testable Unit tests per detector
Medium Offline Operation No network dependencies during analysis phase Architecture review
Medium Minimal Dependencies Self-contained, no external services required Cargo.lock audit

3. Design Rationale

The following table maps each design goal to the architectural decision that satisfies it:

5. Detector Framework

The detector framework implements the Open/Closed Principle: open for extension, closed for modification. This is achieved through a trait-based plugin architecture with zero-boilerplate rule constructors.

5.1 Core Traits

// core.rs

pub trait Detector: Send + Sync {
    fn name(&self) -> &'static str;
    fn detect(&self, ctx: &FileContext) -> Option;
    fn severity(&self) -> Severity {
        Severity::Medium
    }
}

pub struct DetectorRegistry {
    detectors: Vec>,
}

impl DetectorRegistry {
    pub fn register(&mut self, detector: Box);
    pub fn detect(&self, ctx: &FileContext) -> Vec;
}

5.2 Detection Context

Each detector receives a FileContext containing pre-computed file attributes — computed once per file during traversal:

pub struct FileContext<'a> {
    pub path: &'a PathBuf,           // Absolute path (use to read bytes)
    pub relative_path: &'a PathBuf,   // Path relative to image root
    pub mode: u32,                     // Unix permissions
    pub is_executable: bool,
    pub is_world_writable: bool,
    pub is_world_readable: bool,
    pub is_suid: bool,
    pub is_sgid: bool,
}
Design Note: Pre-computing metadata in the scanner provides:
  • Performance: Metadata collected once per file
  • Consistency: All detectors see identical data
  • Simplicity: Detectors need no filesystem operations
  • Safety: Detectors cannot perform arbitrary I/O

5.3 Finding Structure

pub struct Finding {
    pub kind: String,      // Detection type identifier (e.g., "crypto_miner_candidate")
    pub path: PathBuf,     // File path relative to image root
    pub detail: String,    // Human-readable details
    pub severity: Severity,// Critical | High | Medium | Low
}

pub enum Severity {
    Critical,  // Score: 5
    High,       // Score: 4
    Medium,     // Score: 3
    Low,        // Score: 2
}

5.4 Zero-Boilerplate Rule Detectors

Most simple signals (a file matching a path/name pattern) need no custom struct and no trait impl. PathRule pairs a finding rule with a predicate:

registry.register(Box::new(PathRule::new(
    "docker_socket_present",
    Severity::Critical,
    "docker socket exposed",
    |ctx| ctx.normalized_path() == "/var/run/docker.sock",
)));

6. Processing Pipeline

The analysis pipeline follows a strict sequence with well-defined data flow:

Figure 1: Six-stage analysis pipeline from Docker image acquisition through report generation. Stage 0 is optional (skippable via BSUPPLA_SKIP_DOCKER).

6.1 Stage Specifications

Stage 0: Acquisition (optional)

pipeline.rs calls docker pull and docker save to produce the image tar. Skippable via BSUPPLA_SKIP_DOCKER when scanning an existing tar.

Stage 1: Image Loading

Parses the Docker image tar archive using the tar crate (ingest/image.rs). Extracts manifest.json to identify layer paths. Fails fast if manifest missing or malformed.

Stage 2: Layer Verification

ingest/layers.rs verifies all referenced layers exist in the tar archive. Returns error if any layer is missing — prevents partial analysis.

Stage 3: Filesystem Reconstruction

ingest/extract.rs extracts each layer's layer.tar in order. Later layers override earlier ones (standard Docker layer semantics). Output directory is cleaned before each run.

Stage 4: Directory Traversal

scan/scanner.rs builds a single DetectorRegistry (from detectors::default_registry()) and recursively walks the reconstructed filesystem. For each file:

  • Collects file metadata (permissions, size, type) via symlink_metadata
  • Skips symlinks (security boundary)
  • Builds FileContext
  • Passes context to each registered detector
  • Collects all findings

Stage 5: Report Generation

scan/report.rs applies allowlist filtering (scan/allowlist.rs), baseline comparison (scan/baseline.rs), and severity scoring. Outputs findings with suspicion level.

7. Formal Properties & Theorems

Theorem 1: Zero Execution

During analysis, no code from the input Docker image is ever executed.

Proof Sketch: The analysis pipeline only performs read operations on the reconstructed filesystem: symlink_metadata, read_dir, File::open (for ELF header parsing and config file reading). No exec, fork, ptrace, or similar syscalls are invoked. The Detector trait provides no capability to execute code. ∎

Theorem 2: Determinism

For any fixed input image and configuration, bsuppla produces identical findings across runs.

Proof Sketch: All pipeline stages are pure functions of their inputs: (1) tar parsing is deterministic, (2) layer extraction order is fixed by manifest, (3) filesystem walk order is deterministic (directory entries sorted by OS), (4) detector registry is built once with fixed detector order, (5) allowlist/baseline filtering is pure set operations, (6) suspicion level is a pure function of findings. No randomness, timestamps, or external state is used. ∎

Theorem 3: Extensibility (Open/Closed)

Adding a new detection capability requires zero modifications to existing detector, scanner, or pipeline code.

Proof Sketch: New detectors implement the Detector trait (or use PathRule). Registration occurs via a single registry.register() call in detectors::default_registry(). The DetectorRegistry stores Box — the scanner iterates over this collection without knowledge of concrete types. The core module exports all types needed for custom registry composition. ∎

Theorem 4: Isolation

A panic or logic error in one detector cannot affect the execution or results of other detectors.

Proof Sketch: The DetectorRegistry::detect method calls each detector's detect method independently via filter_map. A panic in one detector would unwind the thread, but detectors are Send + Sync and share no mutable state. In practice, all detectors are pure functions of FileContext with no side effects. ∎

Lemma: Suspicion Level Monotonicity

Adding findings never decreases the suspicion level.

Proof: Suspicion level is computed as level(score) = if score ≥ 10 then high else if score ≥ 4 then medium else low, where score = Σ severity_score(f). Since severity_score(f) ≥ 2 for all findings, adding findings increases or maintains the score. The threshold function is monotone non-decreasing. ∎

8. Trust Model

Security Assumption

The Docker image under analysis is treated as untrusted input. The analysis process must never execute any code from the image.

Component Trust Level Rationale
bsuppla Code Trusted Audited, version-controlled, compiled from source
Docker Image Untrusted External input, may be malicious
Docker Daemon Trusted (for Acquire) Required for pull/save; skipped via BSUPPLA_SKIP_DOCKER
Host Kernel Trusted Filesystem operations execute in host context
Analysis Output Trusted Generated by verified code from verified input

8.1 Security Boundaries

  • No Execution: Files are never opened with execute permissions; no execve calls
  • No Network: Analysis phase requires no network connectivity
  • Read-Only: Output directory is cleaned before each run; no writes to source image
  • Symlink Rejection: Symlinks are skipped during traversal to prevent directory traversal
  • Isolated: Should run in containerized or VM-isolated environment for defense-in-depth

9. Extensibility

Two ways to add a signal, both closed against modification of the scanning machinery (scan/, core.rs).

9.1 Simple path/name signal — one line

// In detectors/mod.rs, inside default_registry():
registry.register(Box::new(PathRule::new(
    "docker_socket_present",      // finding kind (allowlist/baseline key)
    Severity::Critical,           // Critical | High | Medium | Low
    "docker socket exposed",      // report detail
    |ctx| ctx.normalized_path() == "/var/run/docker.sock",
)));

9.2 Signal that inspects file contents — custom Detector

use crate::core::{Detector, FileContext, Finding, Severity};

pub struct MyCustomDetector;

impl Detector for MyCustomDetector {
    fn name(&self) -> &'static str {
        "my_custom_detection"
    }

    fn detect(&self, ctx: &FileContext) -> Option {
        if !ctx.normalized_path().ends_with("/etc/thing") {
            return None;
        }
        let bytes = std::fs::read(ctx.path).ok()?;
        // ...analyze bytes...
        Some(Finding::new(
            "my_custom_detection",
            ctx.relative_path.clone(),
            "why it's suspicious".to_string(),
            Severity::High,
        ))
    }
}

Register it (plus the module declaration at the top of detectors/mod.rs):

// In detectors/mod.rs
pub mod my_custom;

pub fn default_registry() -> DetectorRegistry {
    let mut registry = DetectorRegistry::new();
    // ... existing detectors ...
    registry.register(Box::new(my_custom::MyCustomDetector));
    registry
}

Because every type (Detector, DetectorRegistry, PathRule, all detector structs/factories) is public, custom registry composition never requires modifying the crate: build your own registry from bsuppla::core + bsuppla::detectors.

Full recipes with copy-paste examples live in docs/DEVELOPMENT.md.

10. Conclusions

The bsuppla architecture provides:

  • Safe static analysis without code execution (Theorem 1)
  • Deterministic, reproducible results (Theorem 2)
  • Extensible plugin system via trait composition (Theorem 3)
  • Independent testability of each detector
  • Clear separation of concerns with flat module hierarchy
  • Formal verification of critical safety properties

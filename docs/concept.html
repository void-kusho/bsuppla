1. Introduction

bsuppla is built on a foundation of well-established software engineering principles, combined with security-specific design patterns and formal methods. This document explains the theoretical concepts that make bsuppla extensible, testable, and safe.

2. Design Principles

The architecture follows several key design principles, each with formal justification:

2.1 Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification. In bsuppla, this means:

  • Adding new detectors requires no changes to existing code
  • Each detector is isolated in its own module
  • New detection logic is added by implementing the Detector trait or using PathRule
Theorem: OCP Compliance

The DetectorRegistry and scanning pipeline are closed for modification but open for extension via the Detector trait.

Proof: The scanner depends only on the Detector trait (abstraction), not concrete implementations. New detectors are added by registering Box instances. The registry's detect method iterates over the trait object collection without knowledge of concrete types. ∎

2.2 Single Responsibility Principle (SRP)

Each component has a single, well-defined responsibility:

Component Responsibility Invariant
core.rs Shared domain model + detector extension API Zero dependencies on other modules
pipeline.rs Stage orchestration (composition root) Only module depending on both ingest and scan
ingest/* Image acquisition and filesystem reconstruction No detection logic
scan/scanner.rs Filesystem traversal and registry execution No filesystem extraction logic
scan/allowlist.rs, scan/baseline.rs, scan/report.rs Filtering and report generation No filesystem access
detectors/* Specific detection logic implementations Pure functions of FileContext

2.3 Dependency Inversion Principle (DIP)

High-level modules do not depend on low-level modules. Both depend on abstractions. The scanner depends on the Detector trait, not concrete implementations.

3. Detector Algebra

The detector framework can be formalized as an algebraic structure:

Detector Type

A detector is a partial function D: FileContext ⇀ Finding where FileContext is the input domain and Finding is the output codomain.

The Detector trait signature:

pub trait Detector: Send + Sync {
    fn name(&self) -> &'static str;
    fn detect(&self, ctx: &FileContext) -> Option;
    fn severity(&self) -> Severity { Severity::Medium }
}

This forms a category where:

  • Objects: FileContext and Finding
  • Morphisms: Detectors (partial functions)
  • Composition: Not directly supported (detectors are independent)
  • Identity: Trivial detector returning None

3.1 Monoidal Structure of DetectorRegistry

The DetectorRegistry forms a free monoid over the set of detectors:

Registry = (Detectors, ⊕, ε)
where:
  ⊕ = registry.register(d1) ⊕ registry.register(d2)  (concatenation)
  ε = DetectorRegistry::new()  (empty registry)
  det(ε, ctx) = ∅
  det(d1 ⊕ d2, ctx) = det(d1, ctx) ∪ det(d2, ctx)

This monoidal structure guarantees:

  • Associativity: (d1 ⊕ d2) ⊕ d3 = d1 ⊕ (d2 ⊕ d3)
  • Identity: d ⊕ ε = ε ⊕ d = d
  • Commutativity of results: Order of registration doesn't affect detect() output (set union)

3.2 PathRule as Specialized Morphism

PathRule is a specialized detector where the predicate depends only on FileContext::normalized_path():

PathRule = (kind: K, severity: S, detail: D, pred: Path → Bool)
detect(ctx) = if pred(ctx.normalized_path()) then Some(Finding(kind, ctx.relative_path, detail, severity)) else None

4. FileContext Structure

The FileContext provides detectors with pre-computed file metadata — a product type of file attributes:

pub struct FileContext<'a> {
    pub path: &'a PathBuf,           // Absolute path (for reading bytes)
    pub relative_path: &'a PathBuf,   // Relative to scan root
    pub mode: u32,                     // Unix permissions (st_mode)
    pub is_executable: bool,           // mode & 0o111 != 0
    pub is_world_writable: bool,       // mode & 0o002 != 0
    pub is_world_readable: bool,       // mode & 0o004 != 0
    pub is_suid: bool,                 // mode & 0o4000 != 0
    pub is_sgid: bool,                 // mode & 0o2000 != 0
}

4.1 Derived Properties

The following helper methods provide derived views:

impl<'a> FileContext<'a> {
    pub fn normalized_path(&self) -> String {
        // Returns path with leading slash
    }

    pub fn file_name(&self) -> Option<&std::ffi::OsStr> {
        // Extracts filename from path
    }

    pub fn file_name_str(&self) -> Option {
        // Returns filename as String
    }
}

4.2 Why Pre-computed Metadata?

Pre-computing metadata in the scanner provides several benefits grounded in software engineering theory:

  • Performance (Memoization): Metadata is collected once per file via symlink_metadata, avoiding repeated syscalls
  • Consistency (Single Source of Truth): All detectors observe identical attribute values — no TOCTOU races
  • Simplicity (Dependency Injection): Detectors receive context as parameter; no filesystem access needed in detector code
  • Testability (Pure Functions): Detectors become pure functions FileContext → Option, trivially unit-testable

5. DetectorRegistry Composition

The DetectorRegistry manages all registered detectors and provides the main detection interface:

pub struct DetectorRegistry {
    detectors: Vec>,
}

impl DetectorRegistry {
    pub fn new() -> Self;
    pub fn register(&mut self, detector: Box);
    pub fn detect(&self, ctx: &FileContext) -> Vec;
}

5.1 Registration Pattern

Detectors are registered in the default_registry() function — the single composition point:

pub fn default_registry() -> DetectorRegistry {
    let mut registry = DetectorRegistry::new();
    registry.register(Box::new(permissions::SuidSgidDetector));
    registry.register(Box::new(credentials::PrivateKeyDetector));
    // ... more detectors
    registry
}

5.2 Detection Process

When detect() is called, the registry performs a parallel map-reduce:

pub fn detect(&self, ctx: &FileContext) -> Vec {
    self.detectors
        .iter()
        .filter_map(|d| d.detect(ctx))
        .collect()
}

This is equivalent to: detect(reg, ctx) = ⋃_{d ∈ reg} d(ctx) where d(ctx) returns ∅ or {finding}.

The registry is built once per scan and shared across the whole filesystem walk, so detector state (if any) is consistent for every file.

6. Severity Lattice

The severity system forms a bounded join-semilattice:

pub enum Severity {
    Critical,  // Score: 5
    High,       // Score: 4
    Medium,     // Score: 3
    Low,        // Score: 2
}

impl Severity {
    pub fn score(self) -> u32 {
        match self {
            Severity::Critical => 5,
            Severity::High => 4,
            Severity::Medium => 3,
            Severity::Low => 2,
        }
    }
}

6.1 Lattice Properties

  • Partial Order: Low ≤ Medium ≤ High ≤ Critical
  • Join (Least Upper Bound): max(a, b) by score
  • Bottom: Low (score 2)
  • Top: Critical (score 5)

6.2 Score Function

The score function score: Severity → ℕ is a monotone order-embedding:

a ≤ b  ⇒  score(a) ≤ score(b)

7. Suspicion Level Function

The overall suspicion level is computed by a threshold automaton on the sum of finding scores:

fn suspicion_level(findings: &[&Finding]) -> &'static str {
    let mut score = 0u32;
    for f in findings {
        score += f.severity.score();
    }
    
    if score >= 10 { "high" }
    else if score >= 4 { "medium" }
    else { "low" }
}

7.1 Formal Definition

Let F be the set of findings. The suspicion level function L: ℘(F) → {low, medium, high} is:

L(F) = high    if Σ_{f∈F} score(f) ≥ 10
L(F) = medium if 4 ≤ Σ_{f∈F} score(f) < 10
L(F) = low    if Σ_{f∈F} score(f) < 4

7.2 Properties

  • Monotonicity: F₁ ⊆ F₂ ⇒ L(F₁) ≤ L(F₂) (Lemma from Architecture)
  • Thresholds: 3 levels with boundaries at cumulative scores 4 and 10
  • Exit Codes: The suspicion level is informational; the process exits with code 0 on success, non-zero only on runtime errors

7.3 Severity Thresholds Table

Score Range Level Exit Code Interpretation
0-3 Low 0 No significant findings
4-9 Medium 0 Findings present, may warrant review
10+ High 0 Critical findings detected

8. Allowlist as Filter

The allowlist mechanism is a filter function allow: Finding × AllowList → Bool that suppresses known-safe findings.

8.1 Formal Model

An allowlist entry is a pair (kind, pattern) where kind ∈ Kind ∪ {*} and pattern is a glob pattern over normalized paths.

allow(f, AL) = ∃(k, p) ∈ AL : (k = * ∨ k = f.kind) ∧ match(p, f.path)

The default allowlist suppresses elf_suspicious findings in standard library paths:

DefaultAL = {
    (elf_suspicious, "/bin/*"),
    (elf_suspicious, "/sbin/*"),
    (elf_suspicious, "/usr/bin/*"),
    (elf_suspicious, "/usr/sbin/*"),
    (elf_suspicious, "/lib/*"),
    (elf_suspicious, "/usr/lib/*")
}

8.2 Glob Matching Algorithm

The wildcard matcher implements standard glob semantics with * (any sequence) and ? (single character):

match("*", _) = true
match("?", c) = true
match(c, c) = true  (literal char)
match(p₁p₂, s) = ∃i: match(p₁, s[..i]) ∧ match(p₂, s[i..])

9. Baseline as Set Difference

The baseline mechanism computes set differences on finding keys to track changes over time.

9.1 Finding Key

Each finding has a unique key: key(f) = "kind: path"

9.2 Operations

  • Load: load_baseline(path) → Set
  • Diff: diff(F, B) = (F \ B, F ∩ B) — returns (new, known)
  • Missing: missing(F, B) = B \ F — baseline entries not in current scan
  • Export: write_baseline(path, F) — writes sorted keys

9.3 Allowlist-Aware Baseline

Baseline entries suppressed by the allowlist are filtered before diff:

B' = filter_baseline(B, AL) = {k ∈ B | ¬allowlisted(k, AL)}
diff(F, B) = diff(F, B')

11. Extensibility Theory

Adding new detection capabilities is straightforward due to the monoidal registry structure:

11.1 Creating a New Detector

  1. Create a new file in src/detectors/
  2. Implement the Detector trait
  3. Add tests for the detector

11.2 Zero-Boilerplate Rules

For simple path/name signals, no struct or trait impl is needed — a one-line PathRule is enough:

// In default_registry() (detectors/mod.rs)
registry.register(Box::new(PathRule::new(
    "docker_socket_present",
    Severity::Critical,
    "docker socket exposed",
    |ctx| ctx.normalized_path() == "/var/run/docker.sock",
)));

11.3 Custom Registry Composition

Because all types are public, external crates can compose custom registries:

use bsuppla::core::{DetectorRegistry, Severity, PathRule};
use bsuppla::detectors;

fn custom_registry() -> DetectorRegistry {
    let mut reg = DetectorRegistry::new();
    // Use built-in detectors
    for d in detectors::default_registry().detectors() {
        reg.register(d);
    }
    // Add custom
    reg.register(Box::new(PathRule::new(
        "my_custom_signal",
        Severity::High,
        "custom detail",
        |ctx| ctx.file_name_str() == Some("secret".to_string()),
    )));
    reg
}

12. Safety Guarantees

bsuppla is designed with safety as a primary concern, enforced by construction:

12.1 Zero Execution (Theorem 1)

  • Files are never opened with execute permissions
  • No code from the image is ever run
  • Analysis is strictly read-only

12.2 Memory Safety

  • Written in Rust — memory safe by default
  • No unsafe blocks in detection logic
  • All file operations use safe abstractions (std::fs, walkdir)

12.3 Isolation (Theorem 4)

  • Each detector is isolated — one cannot affect another
  • Panics in detectors are contained (though pure functions don't panic)
  • Analysis runs in a controlled order

12.4 No Network Access

  • Analysis phase requires no network connectivity
  • Only Docker operations (pull/save) require network
  • Can be run in air-gapped environments with BSUPPLA_SKIP_DOCKER=1

12.5 Determinism (Theorem 2)

  • Same input image → identical findings
  • No randomness, timestamps, or external state
  • Reproducible across machines and runs

13. Conclusion

bsuppla demonstrates how sound software engineering principles and formal methods can be applied to security tooling. The combination of:

  • Trait-based plugin architecture (monoidal registry)
  • Severity lattice with monotone suspicion function
  • Allowlist as glob-based filter
  • Baseline as set difference
  • Clear separation of concerns (SRP, DIP)
  • Safety-first design (Theorems 1-4)

Results in a tool that is both extensible and trustworthy, with formally verified critical properties.
